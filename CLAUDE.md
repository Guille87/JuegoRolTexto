# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Spanish-language, terminal-based turn-based RPG ("Juego de Batalla por Turnos") written in Python. Uses `colorama` for colored terminal text and `pygame` (mixer only) for background music/SFX — there is no graphical window, the game is played entirely via `input()`/`print()` in the console.

Packaged as an installable Python package (`src/` layout) under `src/juego_rol_texto/`.

## Commands

Setup (Windows, PowerShell):
```powershell
python -m venv env
.\env\Scripts\activate
pip install -e ".[dev]"
```

Run the game:
```bash
python main.py
# or: python -m juego_rol_texto
# or, after install: juego-rol-texto
```

Run tests:
```bash
pytest
```

There is no linter configured in this repo.

## Architecture

**Entry point**: `main.py` at the repo root is a thin compatibility shim that calls `juego_rol_texto.app.main()`. The real entry point is `src/juego_rol_texto/app.py::main()`, which first force-reconfigures `sys.stdout`/`sys.stderr` to UTF-8 (a plain Windows console defaults to a legacy code page that can't encode the emoji used in menu titles — this bit only surfaces outside a UTF-8-safe terminal like PyCharm's, e.g. a packaged `.exe` run from `cmd.exe`, so it's easy to miss in normal dev use), initializes `colorama`/`pygame`, loads saved volume settings (`config/settings.py`), registers all audio assets (`audio/catalog.py`) with `ResourceManager`, then hands off to `ui/menus.py::main_menu()`. Menu "exit" options call `sys.exit()`, not the bare `exit()`/`quit()` builtins — those are `site`-module REPL conveniences that don't exist in a frozen PyInstaller build.

**`config/` — centralized paths and settings**: `config/paths.py` resolves `BASE_DIR`/`ASSETS_DIR`/`SAVE_DIR`/`CONFIG_FILE` as absolute `pathlib.Path`s relative to the repo root, regardless of the process's current working directory. When frozen with PyInstaller (`sys.frozen`), `BASE_DIR` instead resolves to the folder containing the `.exe` (so `config.ini`/`saved_games/` persist next to it across runs) and `ASSETS_DIR` points into the bundle (`sys._MEIPASS`) — see the "Generar un ejecutable" section in `README.md` for the build command; must be `--onedir`, not `--onefile` (the latter re-extracts to a fresh temp folder every launch, losing saves/settings). `config/settings.py` reads/writes volume settings to `config.ini` at `BASE_DIR`.

**`ui/` — presentation layer**: `ui/console.py` centralizes all `colorama` usage behind `success()`/`error()`/`warning()`/`info()`/`title()` (full-line semantic messages) and `colorize(text, color, bright=False)` (inline fragments, used when a single line mixes multiple colors — the dominant pattern in combat/status messages). `ui.console.ask()` wraps `input()`. Domain modules (`player.py`, `battle.py`, enemies, `inventory.py`, `save_load.py`, `menus.py`) import from `ui.console` instead of `colorama` directly, but still print directly from within domain logic — there is **no full MVC separation**; this was a deliberate choice to keep the refactor behavior-preserving rather than an architectural rewrite. `ui/menus.py` is the menu/game-loop hub (former `game_core/menu.py`), `ui/formatting.py` holds the health-bar and detailed-info renderers (former `utils/utils.py`).

**Menu/game loop (`ui/menus.py`)**: Everything is driven by simple numbered `input()`-based menus, no state machine framework.
- `main_menu()` → new game / load game / options / exit
- `start_new_game()` creates a `Player` with base `Stats`; `"admin"` is a **reserved name** — both it and `load_saved_game()` loop on the name prompt and refuse to proceed with that name at all unless `_check_admin_password()` passes (prompted via `getpass.getpass()`, compared as a SHA-256 hash against a constant — the real password is never stored in plaintext anywhere in the repo or the installed game); a wrong password rejects the name outright (the player must pick a different name, or retry `"admin"` with the correct password) rather than silently downgrading to a normal character. Getting it right grants a debug/cheat character (high stats, gold, all 14 enemies unlocked *and* marked defeated including the Dragón) — this is a known intentional test hook, not a bug. That same name+password combo also unlocks a "Panel de Admin" option in `game_loop()` (`_admin_panel_flow` and its `_admin_*` helpers) for full runtime control: set gold/level/any `Stats` field directly, full heal, mass-unlock, fight any enemy in the chain regardless of `unlocked_enemies`, or instantly get 50x of every material (which also discovers every forge recipe, for free, via `Inventory.add_item()`'s existing discovery side effect) and one of every weapon/armor any enemy can drop. The last two force `random.random()` to `0` while reading each enemy's `drop_item()` so every possible item comes out at once, and wrap the bulk `add_item()` calls in `_quiet_pickups()` to silence the per-item "Obtenido: X" print (hundreds of lines otherwise). Loading a save named "admin" still requires re-entering the password (`is_admin` isn't persisted in the save file, and is computed at the name prompt in both `start_new_game()`/`load_saved_game()`, then passed into `game_loop()`). Unrelated to `tools/settings_admin.py` (a Tkinter window, dead code — not imported anywhere, and its field names don't even match `Player`/`Stats`'s real attributes).
- `game_loop(player, unlocked_enemies, defeated_enemies)` is the per-session hub (fight, inventory, equip weapon/armor, options, save, return to main menu). `unlocked_enemies`/`defeated_enemies` are plain lists of enemy name strings threaded through the whole session and persisted on save.
- Enemy names are looked up via a hardcoded Spanish-name → class dict in `_get_enemy_instance()`.

**Combat (`combat/battle.py`)**: `initiate_battle()` is the turn loop entry point.
- `ENEMY_PROGRESSION` dict defines the fixed unlock chain, 14 enemies long, with newer enemies inserted at the tier matching their relative power rather than appended at the end: Goblin → Huargo → Esqueleto → Bandido → Orco → Espíritu Vengativo → Troll → Gárgola → Gólem de Piedra → Mago → Nigromante → Ángel Caído → Demonio → Dragón (final boss, maps to `None`). Beating a new enemy for the first time unlocks the next one and adds it to `unlocked_enemies`.
- **ATB turn system**: each combatant accumulates a `gauge` every tick at a rate proportional to `Player.get_total_speed()` / `enemy.stats.speed`; whoever reaches `ATB_THRESHOLD` (100) first acts, with the overflow carried over (not reset to 0) — this is a Final-Fantasy-X-style "active time battle" where the faster combatant can act multiple times before the slower one gets a single turn, not just a simple alternating order. When both gauges are ready in the same tick, the player's turn (and a flee attempt) always resolves first, so a faster enemy can never interrupt a flee. Fleeing succeeds with probability `min(1.0, player_speed / enemy_speed)`.
- Player stat changes from potions during battle are snapshotted at battle start and restored via `_restore_player()` at battle end (so buffs don't persist outside combat). Post-battle healing (50% of missing HP) also runs there, except after a defeat (already fully healed by `_handle_defeat()`); on a successful flee, `_restore_player(..., max_recovery=...)` caps that healing to only the HP lost *during that specific battle* (tracked via `health_before_battle`, snapshotted at the very start of `initiate_battle()`) — fleeing isn't a win, so it shouldn't also heal damage carried over from earlier fights. A victory triggers an explicit "Presiona Enter para continuar..." pause (`player_won` flag) after all the loot/XP/heal text prints, so the game-loop menu doesn't redraw over it before the player can read what they got.
- **Hit resolution**: `characters/stats.py::resolve_hit(attacker_precision, defender_evasion)` is a shared 100%-base-chance roll (against 0 evasion the attacker always hits; each point of the defender's evasion above the attacker's precision subtracts 1%, floor 5%/ceiling 100%) used by both `combat/battle.py::_execute_turn` (player's standard attack) and `Enemy.perform_turn()`'s default attack, plus most enemy special attacks individually. A handful of unconditional-hit special attacks exist on purpose (e.g. the Gólem's "Terremoto" — thematically an earthquake you can't dodge). `BASE_HIT_CHANCE` used to be 90 (so even 0-evasion targets had a baseline miss chance); changed to 100 on request so evasion is the only source of dodging — this is a global change, and the whole 14-enemy chain was originally calibrated assuming the 90% base (see `TODO.md`'s "Sistema de acierto" section — only the Goblin has been re-verified against the new formula so far).
- **Critical hits are not player-only**: every enemy has its own `crit_chance`/`crit_damage` on `Stats` (rolled the same way as the player's, via `random.random() < crit_chance`, multiplying damage by `crit_damage` on a hit) — `combat/battle.py::_execute_turn` and `Enemy.perform_turn()` both branch on whether the combatant is a `Player` (uses `get_total_crit_*()`, summing equipment) or an enemy (uses the bare `Stats` value, since enemies have no equipment).
- **Physical vs. magical damage and penetration**: `Player.take_damage(amount, is_fire=False, is_magical=False, armor_penetration=0, magic_penetration=0)` and `Enemy.take_damage(...)` (mirrored signature) pick `armor`/`magic_resist` for mitigation based on `is_magical`, then subtract the attacker's matching penetration stat from that mitigation (floored at 0) before applying it. Several enemies now deal magical damage beyond the Mago (e.g. Nigromante's dark bolt, Ángel Caído's holy strike/Juicio Divino, Demonio's summoned lesser demon) — check an enemy's `perform_turn()`/attack helpers rather than assuming only the Mago passes `is_magical=True`. `is_fire` is orthogonal to `is_magical`: it only controls whether the "congelado" status gets melted, unrelated to mitigation.
- Status effects live as dicts in `player.status_effects` (`{"name", "duration", ...}`) and are processed in `Player.on_turn_start()` / `on_turn_end()`. Beyond the original `quemado`/burn, `veneno`/poison, `paralizado`/paralysis, `congelado`/freeze and the potion-driven `regeneración`, several enemies apply their own debuffs via `Player.apply_status(name, duration, power=...)`, each read back by a dedicated `get_total_*()`: `desarmado` (Bandido — zeroes the weapon's damage bonus in `get_attack_range()`), `maldicion` (Espíritu Vengativo — subtracts `power` from `get_total_armor()`), `confusion` (Demonio — subtracts `power` from `get_total_evasion()`).
- "Auto-battle" mode (only unlockable against previously-defeated enemies) polls `msvcrt.kbhit()` each turn to let the player cancel by pressing `q` — this makes `battle.py` Windows-only (`msvcrt` has no cross-platform equivalent here).
- On defeat, the player loses 1/3 of gold and is fully healed rather than getting a game over.

**Characters (`characters/`)**:
- `base.py`: abstract `Character` (name, stats, status_effects) — note `Player` and `Enemy` do NOT actually share this base in practice; `Enemy` (`characters/enemies/enemy_base.py`) is defined independently with its own `take_damage`/`is_alive`. Don't assume polymorphism between `Player` and `Enemy` beyond duck-typing (`is_alive()`, `take_damage()`, `get_attack_damage()`).
- `stats.py`: `Stats` encapsulates HP/attack range/`armor` (physical mitigation)/`magic_resist` (magical mitigation)/`crit_chance`/`crit_damage` (base 0.0 / 1.5x)/`speed` (feeds the ATB gauge, default 10)/`precision`/`evasion` (feed `resolve_hit()`)/`armor_penetration`/`magic_penetration` (reduce the *target's* mitigation, not a defensive stat)/`regen` (passive HP/turn); `health` is a property clamped to `[0, max_health]`. Also hosts the shared `resolve_hit()` function and its constants (`BASE_HIT_CHANCE`/`MIN_HIT_CHANCE`/`MAX_HIT_CHANCE`) — see the Combat section above.
- `player.py`: combat math (attack range including equipped weapon bonus), status effect processing, leveling. `gain_experience()` never resets `self.experience` — it's a cumulative total compared against `required_xp()` on every call (`while self.experience >= self.required_xp(): self._level_up()`), not a per-level cost that gets subtracted. This means `required_xp()`'s output **must** be non-decreasing as level increases, or a single small XP gain can trigger an unintended double level-up (this actually happened during tuning — see below). `Player._required_xp_for_level(level)` (a `@staticmethod`) holds the actual curve; `required_xp()` calls it for the current level and clamps the result to be `>=` the previous level's value via `max()`, guaranteeing monotonicity regardless of what the damping parameters below do. The curve itself: level 1→2 is hardcoded to 8 XP — the minimum a single Goblin kill can grant (`gold_min=4 * 2`), so the very first victory of the game always levels up. Levels 2-9 apply a `damping` multiplier on top of the level≥2 scaling formula — starts at 50% of the normal cost at level 2 (a deliberately calculated midpoint: `98.68 * 0.5 ≈ 49`, between the cheap level 1 and the original undamped level-2 cost of 98) and closes linearly to 100% by level 10 — so there's no jarring cliff right after the cheap level 1 (the original, undamped formula jumped from 8 XP to 375 XP between levels 1→2 and 2→3); level 10+ matches the original, undamped formula exactly, since that's the pacing the late-chain enemies were balanced against. Growth is deterministic but non-uniform per stat via `_growth_gain` (a Pokémon-style `floor(rate * level) - floor(rate * (level-1))` formula, so e.g. a 1.4/level rate produces the fixed sequence 1,2,1,2,1...) — `armor`/`speed`/`min_atk`/`max_atk` grow every level at their own rates, `magic_resist` only every *even* level (deliberate balance against the Mago, not generic growth), and crit/regen/penetration are excluded from leveling on purpose — they stay fixed at their starting value (crit_chance starts at 15% for a new character, set in `ui/menus.py::start_new_game`; regen/penetration start at 0) and only move via equipment.
- **Equipment slots**: `Player.equipped_weapon` (single item, unchanged) + `Player.equipped_armor` — a `dict[str, Item | None]` keyed by `items.equipment.ARMOR_SLOTS` (`casco`, `hombreras`, `peto`, `brazales`, `guantes`, `cinturon`, `perneras`, `botas`, `anillo1`, `anillo2`, `amuleto`; 11 slots, Diablo-3-style). Every `get_total_*()` method on `Player` (`get_total_armor`, `get_total_magic_resist`, `get_total_crit_chance`, `get_total_crit_damage`, `get_total_speed`, `get_total_regen`, `get_total_precision`, `get_total_evasion`, and the armor-sourced part of `get_attack_range()`) sums the base `Stats`/weapon value with the matching bonus from **every** equipped armor piece that has one — most pieces only set a handful of the 11 possible bonus fields on `Armor` (`defense`, `max_health`, `magic_resist`, `crit_chance`, `crit_damage`, `damage`, `element`, `regen`, `speed`, `precision`, `evasion`), the rest default to 0/`None` and contribute nothing. `get_total_armor_penetration()`/`get_total_magic_penetration()` still only return the base `Stats` value — no `Armor` field grants those yet. `get_equipped_element()` checks the weapon first, then falls back to whatever's in the `"brazales"` slot. Max-health bonuses are the one exception to "sum on demand": since `Stats.health`'s setter clamps against `Stats.max_health` and `Stats` has no visibility into equipment, `Armor.use()` directly mutates `player.stats.max_health` (reversing the previous occupant of that slot first, then re-triggering the health setter's clamp via `player.stats.health = player.stats.health`) rather than computing a "total max health" dynamically like the other stats.
- **Every armor slot has a mandatory "base stat"** that every drop for that slot guarantees, on top of 0-3 extra secondary stats (1-4 total, never more): casco→`max_health`, peto→`defense`, hombreras→`precision`, brazales→`crit_chance`, guantes→`crit_damage`, cinturon→`defense` (same field as peto, just flavored as a belt), perneras→`evasion`, botas→`speed`, anillo→`crit_damage`, amuleto→`magic_resist` (`tests/test_armor_progression.py::BASE_STAT_BY_SLOT` is the source of truth). Within a slot, the base stat's magnitude generally doesn't decrease as you move along the 14-enemy chain (mirroring the weapon-damage rule below) — `test_base_stat_does_not_decrease_within_the_same_slot_along_the_chain` enforces this, except two deliberate thematic exceptions tracked in that test's `KNOWN_EXCEPTIONS`: the Mago's peto (a robe shouldn't out-armor a golem's plate — compensated with `magic_resist` instead) and the Gólem's boots (kept deliberately slow — 1 speed, not 0 — to preserve their "trade speed for tankiness" identity against the Huargo's). Stat *count* also loosely trends up along the chain (early-game pieces stay closer to 1-2 stats, late-game ones can reach 3-4) but this isn't a hard rule, unlike the base-stat-present and 1-4-range checks which are.
- **Ring slots are a category, not a 1:1 slot**: unlike the other 9 slots, `anillo1`/`anillo2` both accept any `Armor` whose `.slot == "anillo"` (a marker, not a real key of `equipped_armor`) — `items/equipment.py::slot_accepts(filter_slot, item_slot)` encodes this (rings: category match; everything else: exact match), and both `Inventory.show_inventory()`/`_handle_selection()` filter through it instead of `==`. Because a ring doesn't know by itself which of the two hueco it's going into, `Armor.use(player, target_slot=None)` takes an explicit `target_slot` — `Inventory._handle_selection()` passes the chosen `filter_slot` through for any `Armor`, and `use()` falls back to `self.slot` when `target_slot` is omitted (always correct for the non-ring 1:1 slots). Two rings must have **different names** to be worn simultaneously — `Inventory.add_item()`'s existing "duplicate `Weapon`/`Armor` name auto-sells" rule isn't special-cased for rings, so two copies of the *same* ring can't both be equipped.
- `enemies/`: one file per enemy (14 total — `goblin.py`, `huargo.py`, `skeleton.py`, `bandido.py`, `orc.py`, `espiritu_vengativo.py`, `troll.py`, `gargola.py`, `golem.py`, `mage.py`, `nigromante.py`, `angel_caido.py`, `demonio.py`, `dragon.py`), each subclassing `Enemy` and overriding `perform_turn()`/`drop_item()` for unique mechanics. Common patterns reused across several enemies: a periodic/random "extra hit" that bypasses the normal turn (Huargo's pack bite, Gárgola's charge, Gólem's unavoidable earthquake, Nigromante's/Demonio's summoned ally), a self-heal-under-threshold loop (Mago, Ángel Caído — both learned the hard way that healing + high speed feed back into each other, see `TODO.md`), and an applied-debuff special attack that goes through `resolve_hit()` first (Bandido's `desarmado`, Espíritu Vengativo's `maldicion`, Demonio's `confusion`).
- **Elemental weapon damage** (separate from the Mago's magical damage above — this is a *physical* mechanic): `Enemy.ELEMENTAL_WEAKNESSES` is a class-level `dict[str, float]` (empty = neutral to everything); `Enemy.take_damage(damage, defeated_enemies=None, element=None)` multiplies `damage` by the matching weakness before subtracting armor. The element comes from `Player.get_equipped_element()` (weapon, or brazales as fallback — see above). Elements are bare strings, same pattern as status-effect names — no central registry, each one is just whatever string a weapon's `element` and an enemy's `ELEMENTAL_WEAKNESSES` key agree on. Four exist so far: `Troll` → `"fuego"` (2.0x, the original MVP), `Bandido` → `"veneno"` (2.0x, "un humano de carne y hueso"), `GolemDePiedra` → `"rayo"` (2.0x, "la piedra empapada de minerales conduce mejor que la carne"), `Dragon` → `"hielo"` (2.0x, dragón de fuego débil al hielo clásico). Each element has at least one elemental `Weapon` drop backing it (independent of which enemy is weak to it — e.g. `Huargo` drops a `"veneno"` weapon, `Gárgola` a `"rayo"` one, `Nigromante` a `"hielo"` one; `Orco`/`Dragón`/`Demonio` all drop `"fuego"` weapons). `combat/battle.py::_execute_turn` separately checks `type(defender).ELEMENTAL_WEAKNESSES` *before* calling `take_damage()` to decide whether to print "¡Es supereficaz!" — duplicated because `take_damage()`'s return value doesn't distinguish "no bonus applied" from "bonus applied but armor absorbed it all". All `Enemy` subclasses (including `Skeleton`, which has its own `take_damage` override for its revive mechanic) share the exact same `take_damage()` signature, which is what lets `_execute_turn` call it directly without a `try/except TypeError` fallback.

**Items (`items/`)**: `item_base.py` defines only the abstract `Item` class. `factory.py` holds `item_factory(data)`, a dict → class dispatcher used by save/load to reconstruct items from JSON (`type` field selects the class: `HealingPotion`, `StatBuffPotion`, `RegenPotion`, `Material`, `Weapon`, `Armor`) — it imports the concrete classes at module level (no circular import, since `item_base.py` doesn't import `factory.py`). Every concrete item class implements `to_dict()`/`from_dict()` matching this factory — when adding a new item type, register it in `_ITEM_CLASSES` and implement both methods or save/load will silently drop it.
- `equipment.py`: `Weapon` (damage + optional `element`) and `Armor` (a `slot` from `ARMOR_SLOTS` + any mix of `defense`/`max_health`/`magic_resist`/`crit_chance`/`crit_damage`/`damage`/`element`/`regen`/`speed`/`precision`/`evasion`), equipped via `Inventory.equip_menu()`. `Armor.from_dict()` defaults missing `"slot"` to `"peto"` for saves written before slots existed (see `persistence/save_load.py` below). Also holds `slot_accepts()`/`slot_label()` (see the ring note above) and `SLOT_LABELS` (display-only overrides for the awkward-looking slot keys — `"anillo1"` → `"Anillo 1"`, etc.).
- `potions/`: `potion_base.Potion` (abstract) + `healing_potion.py`, `buff_potion.py` (temporary stat buffs tracked in `player.active_effects`, decremented in `on_turn_end`), `regen_potion.py`.
- `materials.py`: crafting materials, non-usable directly (`use()` always returns `False`) — consumed instead by `crafting/forge.py` recipes.

**Inventory (`inventory/inventory.py`)**: `show_inventory()` prints the player's current/max HP right under the title (so it's easy to judge whether a healing potion is worth using) before listing items. Consumables stack via a `quantities` dict keyed by item name; `Weapon`/`Armor` don't stack — picking up a duplicate auto-sells it for gold instead. `show_inventory(filter_class, filter_slot=None, mode)` is reused both for read-only viewing and interactive selection (`mode="use"`); `filter_class` narrows to `Weapon`/`Armor`, `filter_slot` further narrows an `Armor` listing to a single equipment slot (e.g. only guantes) — both flow through to `_handle_selection()`, which rejects an item whose `slot` doesn't match `filter_slot`. All `Item.use()` implementations return `True` on success, which `_handle_selection()` relies on to decide whether to decrement a consumable from the stack and, in combat, whether the action consumes a turn (`"objeto_usado"`); when adding a new item type, make sure `use()` returns `True`/`False` accordingly. `Inventory.sell_item(item)` (used by the shop) removes one unit via the shared `_remove_one()` helper and credits `item.value` gold — refuses to sell anything currently equipped, checking both `equipped_weapon` and every slot in `equipped_armor`. `has_item(name, quantity)`/`consume_item(name, quantity)` look up and remove stock **by name** rather than by object reference (unlike `_remove_one()`) — used by the crafting system, which knows *what* material it needs but doesn't have a handle to the player's actual item instance.

**Shop (`shop/shop.py`)**: `Shop` holds a fixed, in-memory `catalog` of `ShopItem` (an item template + buy price); wired into `game_loop`'s "Tienda" option via `Shop().open(player)`. Buying clones the template through `items/factory.py::item_factory(template.to_dict())` (so each purchase is an independent instance) and calls the existing `Inventory.add_item()`; selling lists `player.inventory.items` and calls `Inventory.sell_item()`. The catalog is static code, not persisted — `persistence/save_load.py` doesn't know about it. `ShopItem.__str__()` appends `template.get_stats_info()` (same pattern as `CraftingRecipe.__str__()`) so weapons/armor show their actual numbers in the buy menu, not just flavor text — potions "worked" even before this by coincidence, since their `description` already spells out the numbers in prose (e.g. "Restaura 20 HP").

**Crafting (`crafting/forge.py`)**: `Forge` mirrors `Shop`'s structure — a fixed `recipes` list of `CraftingRecipe` (materials-by-name + gold cost + a result item template, cloned the same way as `ShopItem` via `item_factory`), wired into `game_loop`'s "Herrería" option via `Forge().open(player)`. `CraftingRecipe.can_craft(player)` checks gold and `Inventory.has_item()` for every required material; `Forge._craft()` only mutates state (deduct gold, `Inventory.consume_item()` each material, `Inventory.add_item()` the result) after confirming `can_craft()`. 12 recipes exist: 11 `Armor` recipes (one or more per armor slot — peto, hombreras, brazales, guantes, cinturon, perneras, botas, amuleto, plus 3 different anillo recipes) and one `Weapon` recipe ("Daga Envenenada", the only craftable weapon, giving an alternate path to a `"veneno"`-element weapon alongside the Huargo's drop). Collectively they consume all 14 materials from `characters/enemies/*::drop_item()` (one per enemy) — see the recipe list in `Forge.__init__` for exact costs/bonuses. Quantities are deliberately large (15-25 for most materials, down to 2-8 for the rarest drops like Piel de Troll/Esencia Arcana/Escama de Dragón) so that crafting requires actually farming the source enemy rather than a single lucky kill. None of the crafted items grant a passive-effect-per-turn (equipped items have no such hook in the combat loop) — "Armadura Regenerativa" is a plain stat boost despite the name, not literal regeneration. Crafted items are deliberately not always the best option for their slot: e.g. "Cinturón de Resistencia" trades the Gólem drop's raw armor for `magic_resist` instead, so the two aren't strictly comparable (see `TODO.md` for the loot-variety pass that shaped this — every slot now has 2+ drop sources with contrasting stats, not just a single "best" item, on top of its crafting recipe).
- **Recipe discovery**: `Forge.open()` only lists recipes whose materials the player has picked up at least once — `Inventory.discovered_materials` (a `set[str]`) is updated in `add_item()` whenever a `Material` is added, and stays populated even after the material is later consumed crafting. `CraftingRecipe.is_discovered(player)` checks membership for every required material name. This is separate from `can_craft()` (gold + current stock) — a discovered recipe can still be un-craftable if you've spent the materials. Persisted in save/load as `discovered_materials`; old saves without that key backfill it from whatever `Material` items are present in the save at load time.

**Equipping armor (`ui/menus.py::_equip_armor_flow`)**: the "Equipar Armadura" menu option opens a slot-picker submenu (same interactive-loop pattern as `Shop`/`Forge`) listing all 11 `ARMOR_SLOTS` with whatever's currently in each, then calls `player.inventory.equip_menu(Armor, filter_slot=<chosen slot>)` for the chosen one.

**Bestiary (`ui/menus.py::_bestiary_flow`)**: the "Bestiario" menu option is read-only and lists **only** the enemies already in `defeated_enemies` — an unlocked-but-undefeated enemy doesn't appear at all, not even redacted. Picking one builds a throwaway instance via `_get_enemy_instance()` (so its stats reflect the class defaults, not leftover HP from a past fight) and prints its full sheet via `ui/formatting.py::print_bestiary_entry()` — kill count, combat stats, `ELEMENTAL_WEAKNESSES` if any, and gold range. Deliberately excludes the drop table: `drop_item()` doesn't expose its per-item probabilities as static data, and duplicating them here would drift from the real code. `Player.enemy_kill_counts` (a `dict[str, int]`) is incremented in `combat/battle.py::_handle_victory()` on **every** win, unlike `defeated_enemies` which only records the first.

**Save/load (`persistence/save_load.py`)**: game state is serialized to JSON, then base64-encoded, written to `saved_games/<player_name>.sav`. Saving always backs up the previous file to `<player_name>.bak` first; loading falls back to the `.bak` file if the `.sav` fails with an error *not* in `{json.JSONDecodeError, binascii.Error, UnicodeDecodeError, KeyError}` (those specific failures return `None` immediately without a fallback attempt — this is existing, deliberately-preserved behavior, not something to "fix" silently). Item reconstruction goes through `items/factory.py::item_factory`. `equipped_armor` is saved as `{slot: item_dict_or_null}`; on load, a dict containing a `"type"` key (the pre-slots format, a single armor item) is treated as legacy and placed into the `"peto"` slot — this is the only place in the codebase that has to distinguish old vs. new save-file shapes rather than just defaulting missing keys.

**Audio (`audio/resource_manager.py`)**: `ResourceManager` is a singleton (`__new__` override). Music tracks go through the dedicated `pygame.mixer.music` stream (one track loaded/playing at a time, loaded on demand from `music_paths[name]` in `play_music()`); SFX are separate `pygame.mixer.Sound` objects played on the regular channel pool via `play_sfx()`. This split matters: `pygame.mixer.music.get_busy()` only reflects the music stream, so an SFX playing concurrently (e.g. a hit sound mid-combat) never masks "the track has ended" — using `pygame.mixer.get_busy()` (any channel) here was a real bug fixed in a past session, since a busy SFX channel could block the mood system from ever detecting the track had finished. It self-manages background music via a `mood` field (`"adventure"` vs `"battle"`) — `update()` only acts once `pygame.mixer.music.get_busy()` is `False` (current track ended), picking a new one via `play_random_adventure_music()` or `play_battle_music(target_enemy)`. Entering combat calls `play_battle_music()` directly (bypassing the busy-check) so the switch to combat music is instant rather than waiting for whatever was already playing to finish. `update()` is called from `app.py::main()` once at startup, from `main_menu()`'s and `game_loop()`'s loops, from inside `initiate_battle()`'s turn loop, and — since this is a synchronous console app that spends most of its time blocked on `input()` — from a daemon thread (`app.py::_music_watchdog`) that calls it every 2s so tracks still auto-advance while the game is just waiting on the player. Volumes persist to `config.ini` via `config/settings.py`. `audio/catalog.py` holds the `AUDIO_ASSETS` dict of relative asset paths.

## Tests (`tests/`)

`pytest`-based. `tests/conftest.py` sets `SDL_AUDIODRIVER=dummy` and initializes `pygame.mixer` headlessly (session-scoped autouse fixture) so `ResourceManager`/`battle.py` can run without real audio hardware, and provides a `tmp_save_dir` fixture that monkeypatches `juego_rol_texto.persistence.save_load.SAVE_DIR` so save/load tests never touch the real `saved_games/` directory. Coverage: `Stats` clamping, `Player` combat math/status effects/leveling, `Inventory` stacking/equip/use/sell/craft-support flows, `Shop` buy/sell flows, `Forge` crafting flows, item `to_dict()`/`from_dict()` round-trips through `item_factory`, save/load round-trip + backup fallback, and `initiate_battle()` victory/defeat outcomes (enemy unlock progression, gold penalty on defeat, elemental weakness bonus) using deterministic fixtures (`weak_enemy`) and `monkeypatch` for `input()`/`time.sleep()`/`random`.

## Known incomplete/dead areas (see TODO.md)

- `tools/settings_admin.py` (a Tkinter debug settings window) is not imported anywhere in the game; it's leftover/experimental.
- Combat is strictly 1-vs-1: there's no real concept of multiple simultaneous enemies. Several enemies fake it with an "extra hit" pattern instead (a summoned ally or pack member attacks immediately as part of the same turn, rather than existing as a separate combatant with its own gauge/turns) — see the `enemies/` bullet above.
- Equipment set bonuses (2/4/6-piece bonuses for wearing multiple items from the same themed set) are a planned feature, discussed with the user but not yet designed or started — today every armor piece is independent, no `set` concept exists on `Armor`.
- `TODO.md` tracks the detailed history of balance passes (per-enemy playtest numbers, why specific stat values were chosen) — worth checking before re-tuning an enemy or item, since the reasoning (and the pitfalls already hit) is usually documented there rather than in code comments.
